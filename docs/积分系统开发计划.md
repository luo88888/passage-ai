## 一、背景与目标

当前系统采用「配额（quota）」模式：普通用户创建文章时扣 1 次配额，VIP/管理员不限量。
配额粒度太粗，无法区分不同模型的成本差异（标题/大纲/正文/信息采集/配图模型价格不同、token 消耗量差异巨大）。

本次开发目标：

1. **统计用户各模型使用情况**：记录每个用户每次生成任务中，各 LLM / AI 生图模型的调用次数、token 消耗、耗时。
2. **转化为积分**：为每个模型配置积分单价，按实际用量实时换算成积分消耗。
3. **积分不足暂停生成文章功能**：创建文章前校验积分余额，不足则拦截并给出明确提示。

同时为 TODO 中「签到赠送积分」「积分明细查询」预留扩展点（本期实现签到与明细；**积分充值暂不实现**，后续迭代再接入支付）。

## 三、总体方案

### 3.1 积分模型（余额制 + 后付费结算）

采用**预付费积分余额 + 后付费段级结算**模型：

- 每个用户一个积分账户 `user_points`（余额 balance、累计获得、累计消耗；**余额允许为负**，最多透支 `MAX_DEBT_POINTS`（默认 100）积分）。
- 新用户注册赠送 **100 积分**（100 积分 = 1 元）。
- 签到每日赠送 **10 积分**（每日一次）。
- **创建不预扣、不估算**：创建时仅校验 `balance >= 0`；任务运行按实际用量记账，在**每个计费段边界（含每次 AI 修改轮次）即时结算**，余额不足允许小额透支付费。
- 计价按「积分 / 千 token」配置；按**计费段**汇总各模型总 token 后一次性计算并向上取整（有消耗但不足 1 积分按 1 积分扣），避免逐次向上取整放大成本。
- **透支护栏**：`balance < 0` 禁止新建文章；`balance < -MAX_DEBT_POINTS` 禁止续跑（确认标题/大纲、AI 修改等）；欠费用户签到/充值还清后方可再创作。
- **并发限制**：单个用户「进行中（含挂起）」创作任务上限 `MAX_ACTIVE_TASKS`（默认 5）个，超出拒绝创建；用 MySQL `user.activeTaskCount` 原子计数，服务重启依然准确。
- **全员按积分消耗**：VIP 与普通用户同价扣积分；仅**管理员**豁免（运维账号，不参与计费、不限并发）。
- 历史 `quota` 余额按 1 quota = 100 积分一次性折算到新账户，之后创建校验改用积分，`quota` 列保留兼容不再作为门槛。

### 3.2 关键决策（本期默认假设，需产品确认）

| 决策点 | 默认方案 |
| --- | --- |
| VIP 是否扣积分 | 扣（与普通用户同价），仅管理员豁免 |
| 免费配图（Pexels/Iconify/表情包/Mermaid本地） | 已确认：不扣积分，仅统计 |
| AI 生图（智谱/Nano Banana） | 智谱免费；Nano Banana 2 积分/张 |
| 结算模型 | **后付费段级结算**：不预扣、不估算；按实际用量结算，余额允许小额透支（`MAX_DEBT_POINTS`=100） |
| 透支护栏 | `balance < 0` 禁新建；`balance < -100` 禁续跑/禁 AI 修改 |
| 并发限制 | 进行中（含挂起）任务上限 5 个/用户；MySQL `user.activeTaskCount` 原子计数，重启准确 |
| AI 修改类动作 | 每轮修改结束**即时结算**（点一次收一次），修改前检查余额 |
| 图挂起 | 每次图挂起时进行一次结算 |
| token 计量 | 优先取响应 `usage_metadata`，缺失时按字符数估算兜底 |
| 积分取整规则 | 计费段级汇总总 token 一次向上取整，不足 1 积分扣 1 积分 |

| --- | --- | --- | --- | --- |

| mimo-v2.5-pro | 大纲/正文/图片分析/AI改大纲/采集主Agent | 1 | 2 | 输入 1000 积分/百万token，输出 2000 积分/百万token |
| deepseek-v4-flash | 备用 | 0.3 | 0.6 | 单价对齐 mimo-v2.5 |
| *（LLM兜底） | 未知模型 | 1 | 2 | 兜底规则（同主力模型） |

> 单价支持小数（DECIMAL 存储）；同一计费段各模型聚合总 token 后一次性计算并向上取整（不足 1 积分扣 1 积分）。

### 5.2 埋点设计（新增 `backend/app/services/model_usage_service.py`）

- 新增 `UsageRecorder`：内存中按 `taskId` 聚合本次任务用量（`dict[taskKey, Accumulator]`），任务结束后一次性落库，避免每条调用都写库；**M3 起落库粒度调整为按「计费段」增量落库（结算水位），见 6.2**。
- 文本类统一在 `BaseAgent._call_llm / _call_llm_with_streaming` 出口处上报（agent_name 由调用方传入，model 从 `self.model.model_name` 或配置中取）。
- 流式响应逐 chunk 累加 `usage_metadata`（LangChain `AIMessage.usage_metadata` 含 `input_tokens/output_tokens`）。
- 信息采集子 Agent 的多次并行调用按工具调用次数聚合。
- 图片类在服务层每次成功生成后上报 `imageCount=1`。
- `userId` 解析：通过 `taskId` 查 `article.userId`（创建任务时写入内存缓存 `taskId→userId`，finalize 清理），保证埋点不侵入图节点。

### 5.3 Token 获取与兜底

1. 优先：响应对象 `usage_metadata`（OpenAI 兼容接口均会返回）。
2. 兜底：无 usage 时按 `ceil(字符数 / 3)` 估算 input/output token。
3. 失败/异常调用也记录 `status=FAILED`（不计积分或按配置半价，默认不计费）。

## 六、积分计算与结算

### 6.1 计价规则

- LLM（按千 token，单价可为小数）：先按模型聚合**计费段内**总用量，`cost_model = inputTokens/1000 * inputPricePer1k + outputTokens/1000 * outputPricePer1k`，段总成本 `cost = Σ cost_model`（多模型相加），最终一次性取整 `costPoints = ceil(cost)`；有消耗但 `cost < 1` 时按 1 积分扣除。**同一计费段只取整一次**。
- 生图：`cost = imageCount * pricePerImage`（智谱免费 = 0；Nano Banana = 2 积分/张）。
- 匹配优先级：`model_pricing` 中 `(category, provider, model, agentName)` 精确匹配 → `(category, provider, model, NULL)` → `(category, provider, '*', NULL)` 兜底；未命中按系统默认单价。

### 6.2 后付费段级结算流程（取代 v1.2 预扣-结算）

```
POST /article/create
  ├─ 1. Depends 拦截：balance >= 0 且 activeTaskCount < MAX_ACTIVE_TASKS（快速失败）
  ├─ 2. 事务内：acquire_task_slot（activeTaskCount+1，原子校验 < 5）+ INSERT article(PENDING)
  └─ 3. 启动图任务，不预扣、不冻结

计费段（每段结束做一次增量结算）:
  ├─ 段A 标题生成（create → confirm_title 挂起）
  ├─ 段B 大纲生成 + AI 修改大纲每轮（confirm_title → confirm_outline）
  ├─ 段C 正文生成 + 配图 + 合并（confirm_outline → finalize）
  └─ 每个段边界：从 UsageRecorder 取「上次结算点之后」的新增用量 → 计价 → 扣费
       （允许负余额，balance >= -MAX_DEBT_POINTS）→ 记 USAGE_SETTLE 流水 → 更新结算水位

任务终态（finalize / _handle_failure / delete）:
  ├─ 结算剩余未结算用量（如有）
  └─ release_task_slot（activeTaskCount-1，与状态变更同事务）
```

- **结算粒度**：按「计费段」增量结算（段级取整，见 6.1）；AI 修改大纲/正文/配图等**可无限循环**的动作每轮结束即时结算（点一次收一次），防止循环内费用无界累积。
- **透支出账**：结算时余额可为负，受 `-MAX_DEBT_POINTS` 约束；欠费在下次创建前必须还清（签到/充值）。
- **失败/删除**：按已发生用量结算 + 释放名额。
- **并发安全**：`user_points.balance` 更新用行锁 `SELECT ... FOR UPDATE`（或乐观锁）；结算幂等（按任务「已结算水位」），避免重复扣费。
- **管理员豁免**：admin 跳过结算与并发限制（视为无限余额、不限任务数）；VIP 与普通用户均按积分结算。

### 6.3 透支护栏（积分不足暂停机制）

1. **新建主闸门**：`balance < 0` 拒绝创建，提示「当前欠费 X 积分，请先签到/充值」（充值暂未开放，签到每日 10 积分）。
2. **续跑/修改检查**：`confirm-title`、`confirm-outline`、`ai-modify-outline`（及将来 ai-modify-content/images）前检查 `balance + MAX_DEBT_POINTS >= 0`，不满足拒绝续跑/修改并提示积分不足，在路由层进行拦截。
3. **前端配合**：创作页展示余额与可透支额度、进行中任务数；欠费/超并发时禁用「开始创作」并给出签到引导。

### 6.4 并发限制（核心：服务重启准确计数）

**目标**：单个用户同时「进行中（含挂起）」的创作任务（`status IN ('PENDING','PROCESSING') AND isDelete = 0`）最多 `MAX_ACTIVE_TASKS`（默认 5）个；限制的是**未完成的创作任务**，包括挂起等待确认的任务。

**选型**：以 MySQL `user.activeTaskCount` 为唯一事实源（原子 UPDATE，复用 quota 扣减模式），**不用 Redis 计数**（Redis 无法与文章状态同事务，重启/持久化/漂移风险高）。

**核心 SQL**：

```sql
-- 占用（原子「检查 + 自增」，返回影响行数：1=成功，0=超限）
UPDATE user SET activeTaskCount = activeTaskCount + 1
WHERE id = :userId AND isDelete = 0 AND activeTaskCount < :maxActiveTasks;

-- 释放（幂等，GREATEST 防负数）
UPDATE user SET activeTaskCount = GREATEST(activeTaskCount - 1, 0)
WHERE id = :userId AND activeTaskCount > 0;

-- 启动对账（把计数纠正到与 article 表一致）
UPDATE user u SET activeTaskCount = (
    SELECT COUNT(*) FROM article a
    WHERE a.userId = u.id AND a.status IN ('PENDING','PROCESSING') AND a.isDelete = 0
);
```

**占用/释放时机**：

- 占用：创建文章时，`acquire_task_slot` 与 INSERT article **同一事务**（任一失败整体回滚，计数不泄漏）。
- 释放：`finalize`（COMPLETED）、`_handle_failure`（FAILED）、`delete_article`（isDelete=1），均与状态变更**同一事务**。
- admin 豁免（不计数、不限制）。

**重启一致性**：计数持久化在 MySQL，重启不丢；lifespan 启动时执行对账，修复历史漂移与僵尸任务；重启中断的图任务可经 SQLite checkpointer 断点续跑。

**路由层拦截**：`deps.py` 新增 `require_create_slot`（读 `activeTaskCount < MAX` + `balance >= 0` 快速失败），挂到 `POST /article/create`；续跑接口不检查并发（任务已占名额），仅保留归属/阶段校验。

## 十、测试与验收

### 核心用例
1. 新用户注册 → 账户余额 = 100 积分，有赠送流水。
2. 创建文章（余额 ≥ 0）→ 不预扣、不冻结；任务完成按实际用量段级结算，记 `USAGE_SETTLE` 流水，`model_usage_record` 各模型记录正确。
3. 创建文章（余额 < 0 欠费）→ 返回 `INSUFFICIENT_POINTS`，任务未创建，无扣分。
4. 任务中途失败 → 按已发生用量结算（余额可变为负），无退补环节。
5. AI 修改大纲 → 每轮结束即时结算；余额 < -MAX_DEBT_POINTS 时拒绝下次修改/续跑。
6. 管理员 → 不扣积分、不受余额限制、不限并发；VIP 与普通用户同样按积分结算。
7. 签到 → 每日一次，重复签到被拒，余额+10；欠费用户签到后余额回正可再创作。
8. 并发创建 → 第 6 个「进行中/挂起」任务被拒；`activeTaskCount` 在成功/失败/删除后正确回落。
9. 服务重启 → 重启后 `activeTaskCount` 与 DB 中进行中任务数一致。
10. 取整规则：同一计费段多次小量调用按总 token 汇总后一次取整（如 10 次各输出 100 token 的 mimo-v2.5，总 0.6 积分 → 取整扣 1 积分，而非逐次取整的 10 积分）。
11. deepseek-v4-flash 按 mimo-v2.5 单价结算（0.3/0.6 积分每千 token）；Nano Banana 每张扣 2 积分。

- [ ] 积分不足时无法创建文章，且提示清晰、可跳转签到（充值暂未开放）。

## 十一、风险与注意事项

1. **计价不准确**：模型真实成本波动大，需定期按 API 账单校准 `model_pricing`；建议上线初期设保守单价。
2. **token 计量偏差**：部分 provider 流式响应可能不返回 usage，兜底估算会有偏差；建议记录 `usageSource`（api/estimate）便于对账。
3. **埋点遗漏**：新增 Agent/模型时容易漏接埋点，建议在 `llm_factory.get_chat_model` 外层做统一包装（装饰器），新模型自动覆盖。
4. **结算一致性**：段级结算必须走行锁/乐观锁；结算与图任务解耦，结算失败要有重试/补偿（按任务「已结算水位」幂等，防重复扣费）。
5. **透支风险**：余额可为负 = 允许用户先享后付，靠 `MAX_DEBT_POINTS`（100 积分 = 1 元）上限 + 并发限制（同时最多 5 个任务）把坏账收敛到可控范围；欠费用户禁止新建直到还清。
6. **并发计数漂移**：`activeTaskCount` 必须与 article 状态同事务变更；启动对账。
7. **历史数据**：`model_usage_record` 只统计新部署后的数据，历史文章无用量记录，属预期行为。
8. **会员权益**：VIP 现改为按积分消耗，其权益聚焦「解锁高级配图（Nano Banana/SVG 等）」，上线前需同步更新会员权益说明，避免已购用户预期落差。
